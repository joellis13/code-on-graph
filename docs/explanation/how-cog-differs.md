# How cog Differs

**Type:** Explanation · **Status:** Draft v1 · **Last updated:** 2026-10-15

Why build `cog` when AI coding agents already exist? This page names the characteristics that set it apart, shows where each one is enforced, and says plainly where typical agent tools are stronger today and what `cog` does about it. It is the one place for this comparison; other pages link here.

"Typical agent tools" means the common shape of today's products (Claude Code, Copilot, Antigravity, Cursor, Aider, and similar): one conversational loop in which a model searches, decides, edits, and runs commands, while a human steers through chat and permission prompts. Many of those products have parts of what follows, such as plan modes, hooks, and permission rules. The difference is that `cog` makes them **structural and checked by code**, not optional or enforced only by a prompt.

## 1. Distinguishing characteristics

| #   | Characteristic                                  | Typical agent tool                                                                                      | cog                                                                                                                                                                                                                                           | Enforced in                                                                                                                                                                                           |
| --- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **Planning and execution are separate**         | A plan, if any, lives in the conversation and is carried out by the same loop                           | A plan is a durable, immutable, versioned JSON artifact. A human approves a specific plan hash, and Implementation verifies that hash before it executes anything                                                                             | [ADR-0007](../decisions/0007-plans-as-immutable-json.md); Planning nodes 21–22; [Implementation outline](../workflows/implementation/outline.md), Section 2                                           |
| 2   | **LLM outputs are proposals that code checks**  | The model's claims ("this file exists", "this function is called X") are trusted until something breaks | Every path, symbol, and command the planner names is checked against the index at `base_sha` before anything depends on it. Failures return to the planner as precise errors, a bounded number of times                                       | [Planning principle 8](../workflows/planning/reference.md#1-purpose-and-principles); node 18                                                                                                          |
| 3   | **Requirements are anchored to the issue**      | The model restates the request in its own words                                                         | Each requirement carries a verbatim quote from the issue, a comment, or a human answer, and code checks that the quote exists. Anything inferred is an assumption, shown separately. Checklist items no requirement covers are flagged        | Node 18, checks 12 and 13                                                                                                                                                                             |
| 4   | **The model never writes commands**             | The model writes shell commands; permission prompts gate them                                           | Acceptance checks name entries in a command table discovered from the repo's own build files. `cog` builds the argument list                                                                                                                  | [ADR-0019](../decisions/0019-acceptance-checks-reference-the-command-table.md)                                                                                                                        |
| 5   | **Structure is derived by code**                | The model decides order and parallelism                                                                 | Dependency order, parallel batches, and write-set conflicts are computed from `depends_on`                                                                                                                                                    | Node 17                                                                                                                                                                                               |
| 6   | **Context is built deterministically and kept** | The model searches until it judges it is done; what it saw is scattered through a transcript            | Retrievers with provenance build the context before the model is called. The exact packed context is stored by hash, so a run can be replayed and model or prompt changes compared on identical inputs                                        | Nodes 1–12; [Indexing](indexing.md)                                                                                                                                                                   |
| 7   | **Everything is bounded**                       | Turn or spend limits, where they exist, end the session                                                 | Every loop has a fixed cap. Per-run and per-node token and dollar caps pause the run for a human decision. Cost is recorded per node, and unknown cost is recorded as unknown, never as zero                                                  | [Planning reference](../workflows/planning/reference.md), Section 5; [Providers](providers.md), Section 6                                                                                             |
| 8   | **Review comes from another model family**      | Self-review by the same model, if any                                                                   | An optional reviewer from a different family lists the requirements it finds in the issue without seeing the planner's list, then compares. It is advisory and runs after the deterministic checks                                            | Node 19                                                                                                                                                                                               |
| 9   | **No code-style opinions**                      | Style preferences built into system prompts                                                             | Prompts and defaults carry no style opinions. The harness owns process quality; the repo owns code quality                                                                             | [ADR-0014](../decisions/0014-repo-convention-precedence.md)                                                                                                                                           |
| 10  | **cog owns the loop and is model-agnostic**     | One vendor's prompts, tools, and models, tuned together                                                 | `cog`'s own prompts and tools. Roles resolve to tiers and then to any configured provider, so cheap models can do work that code verifies. Vendor agents are optional runners and baselines                                                   | [ADR-0004](../decisions/0004-two-provider-interfaces.md), [ADR-0005](../decisions/0005-direct-providers-first.md), [Architecture](architecture.md), Section 1                                         |
| 11  | **Local-first and auditable**                   | Transcripts live in the product; telemetry goes to the vendor                                           | Every node, model call, tool call, and GitHub call is recorded locally in SQLite, with payloads stored by hash. Secrets are redacted before anything leaves the machine and in storage. Nothing is written to a target repo without a request | [ADR-0006](../decisions/0006-local-first-storage-no-logging-service.md), [ADR-0016](../decisions/0016-secret-redaction.md), [ADR-0008](../decisions/0008-standalone-command-center-managed-clones.md) |
| 12  | **Quality is measured, not assumed**            | Quality claims are anecdotes or vendor benchmarks                                                       | Context recall against historical merged PRs, per-retriever ablations, and baselines against agentic search and commercial agents on the same issues                                                                                          | [Testing and evaluation](testing-and-evaluation.md), Sections 9 and 10                                                                                                                                |

### What this buys

- **Trust you can check.** A reviewer sees which claims were verified, which requirements trace to which quote, and which context each task relied on.
- **Cheaper models.** When code verifies structure, paths, and commands, a smaller model can do more of the work.
- **Containment of prompt injection.** The planner has read-only tools, no network, and no way to author a command; a human approves a hashed artifact.
- **Debuggability and comparison.** Stored context snapshots and per-node events make a bad plan explainable and two prompt or model versions comparable on identical inputs.

## 2. Where typical agent tools are stronger

The same structure that makes `cog` checkable costs flexibility. These are the gaps, with what `cog` does or could do about each.

**Status:** _Planned_ means the roadmap includes it. _Proposed_ means it is recommended but not yet decided by the owner. _Open_ means it needs design.

| Gap                                   | Why typical tools are stronger                                                                    | Mitigation                                                                                                                                                                                                                                                                                                                                                                                                       | Status                                    |
| ------------------------------------- | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| **Iterating on a plan**               | You refine a plan in conversation, a sentence at a time                                           | Reject with feedback already re-runs from the planner (node 15) on the stored context, without re-retrieval. Add feedback aimed at one task (`--task T3`), and a `cog plan edit` that opens a human-friendly rendering (YAML) in your editor, then converts and re-validates it instead of asking you to hand-edit JSON                                                                                          | Proposed                                  |
| **Exploring vague issues**            | An agent follows leads: it reads a file, sees a call, opens the callee                            | The planner has a small read-only tool budget and two gap rounds. The Phase 3 agentic-search baseline measures whether that is enough. If agentic search wins on vague issues, raise the budget or add a bounded agentic gap-filling mode, measured like any other change                                                                                                                                        | Planned (Phase 3 baseline)                |
| **Running code while planning**       | An agent can reproduce a bug, run the failing test, or try the app before deciding what to change | Planning stays execution-free (that is what makes it safe to run on untrusted issues). Implementation can close most of the gap: a "reproduce first" step for bug issues (the first task writes a failing test, and the executor confirms it fails before fixing it), and the baseline run of the repo's gates before any change ([ADR-0014](../decisions/0014-repo-convention-precedence.md), Round 4 addendum) | Proposed (Implementation design)          |
| **Edit reliability and model tuning** | Vendors tune prompts, tools, and edit formats with their own models                               | `NativeRunner` adopts edit formats with a track record (search-and-replace blocks with tolerant matching, whole-file for small files), keeps per-model-family prompt overrides, and is measured against Claude Code and Copilot as baselines. The Phase 3 execution trial tests plans on existing runners first                                                                                                  | Planned (Phase 3 trial, Phase 6)          |
| **Time to first result**              | An agent works in any directory immediately                                                       | `cog` needs `cog repo add`, an index, and optionally a mirror. The thin index (`git grep` at `base_sha`) works at once, the mirror is optional (`related_issues` returns `skipped`), and `cog index build` can run ahead. Also track time-to-first-plan as a Phase 2 metric, and have `cog plan` offer to register an unknown repo                                                                               | Partly planned; metric and offer proposed |
| **Inputs other than a GitHub issue**  | Any free-text request works                                                                       | `cog plan --file request.md`: a local text file stands in for the issue. Requirement anchoring works against its text; GitHub-only retrievers return `skipped`                                                                                                                                                                                                                                                   | Proposed                                  |
| **External knowledge**                | Agents can search the web and read library documentation                                          | The planner has no network, by design. A deterministic retriever could read dependency sources or docs that the build already downloaded, or fetch an allow-listed list of documentation URLs from config, under the egress policy. Code fetches; the model never does                                                                                                                                           | Open                                      |
| **Learning across sessions**          | Memory files and learned preferences carry over between sessions                                  | Your review edits and reject feedback are already recorded. Mine them per repo into **suggested** repo notes that you approve into the local per-repo config. Never automatic, and never style opinions from the harness                                                                                                                                                                                         | Proposed                                  |
| **Editor integration and polish**     | Inline diffs, IDE panels, and rich terminal interfaces                                            | The CLI is deliberately plain. The planned MCP server lets an editor agent (Claude Code, Copilot) call `cog`'s planning as a tool, so `cog` can live inside those tools instead of competing with them ([Interaction model](interaction-model.md), Section 7)                                                                                                                                                    | Planned (later interface)                 |

### What not to copy

Chat as the primary interface, model-authored commands, unbounded agent loops, and style opinions in prompts. Each would trade away one of the characteristics in Section 1.
